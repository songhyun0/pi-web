# Implementation roadmap and quality gates

## Purpose

Define the implementation document set, phase ownership, dependency order, traceability expectations, and stop/go gates for session capability profiles.

This roadmap is cross-cutting. It does not define schemas, runtime code, UI behavior, or migration mechanics beyond sequencing and quality gates. Those details belong in the phase documents listed below. It also assigns cross-cutting ownership for server-side source of truth, fail-closed error handling, preview/runtime consistency, and runtime tool-policy consistency.

### Cross-cutting ownership gates

- Canonical types: `01` owns profile-definition types (`ProfileRef`, `ToolPreset`, `PackageSource`, `SkillRef`, `ProfileDefinition`, `ProfilesFileV1`). `03` owns snapshot-specific types (`CapabilitySnapshotV1`, `ToolConflict`, `ProfileDiagnostic`, snapshot store records, and write tokens). Other phases must reference those owners instead of redefining shapes.
- Server source of truth: `01` owns profile/default files, `03` owns session snapshot files, and `07` must treat localStorage only as a visible last-used selection convenience for new sessions. Gates must prove server defaults/snapshots win over cached UI state.
- Missing profile file: `01` may provide raw-store missing-file handling and pre-bootstrap fallback behavior. The final shared bootstrap behavior that writes the initial real default profile belongs to `09` and must be used by profile-resolution/API paths after `09` is implemented.
- Error handling: `02` owns preview diagnostics, including unknown plugin tool metadata blocking rules; `05` owns new-session fail-closed behavior; `06` owns existing-session apply/restore failures; `07` owns user-facing error states; and `10` verifies the full matrix.
- Preview/runtime consistency: `02` defines resolver behavior using the `03` snapshot/diagnostic contracts; `04` owns the runtime tool-policy helper and minimum `get_tools` metadata contract; `05`/`06` must call that helper when creating/restoring/switching runtimes.

## Implementation steps

1. Draft phase documents using the fixed compact template:
   - Purpose
   - In-scope work
   - Out-of-scope / handoff boundaries
   - Dependencies on prior phases
   - Implementation tasks
   - Tests / evidence required
   - Invariants covered
   - Stop/go gate
2. Enforce phase ownership boundaries:
   - `01` owns canonical profile schema/store/API definitions and the server-side global default source.
   - `02` owns preview and diagnostics, but must not persist snapshots or mutate settings. It consumes `03` snapshot/diagnostic/conflict contracts.
   - `03` owns canonical snapshot-specific types, snapshot storage/API shape, CAS/write-token behavior, and server-side session snapshot authority; it does not own package resolution or runtime service creation.
   - `04` owns pre-resource-load package/settings integration, runtime tool-policy reapplication helper, minimum runtime tool metadata contract, and reload/late-registration enforcement points; it does not own new-session or existing-session transaction orchestration.
   - `05` owns new-session transactional application and explicit profile resolution failure behavior.
   - `06` owns existing-session restore/switch/rollback, running `409`, and legacy restore runtime behavior.
   - `07` owns selector, manager, wizard, hooks, primary UI state flow, server-backed global default UI, localStorage-as-cache-only behavior, and user-facing errors.
   - `08` owns diagnostics/conflict display polish, not core diagnostic generation or runtime metadata enforcement.
   - `09` owns migration bootstrap and legacy-exit verification. Bootstrap depends on `01` raw store/profile schema and `03` snapshot contracts; legacy restore verification depends on `04` and `06`.
   - `10` owns final validation, regression evidence, and local pi-web smoke test evidence.
3. Require every phase doc to include:
   - `Covers: Ix, Iy` for directly implemented invariants.
   - `Must not violate: Ix, Iy` for relevant constraints owned elsewhere.
   - A stop/go gate that blocks dependent phases if objective evidence is missing.
4. Review in three passes before implementation begins:
   - Per-doc drift review against the design and invariant list.
   - Cross-doc overlap review for duplicated or conflicting ownership.
   - Set-level completeness review to verify all source requirements are covered exactly once or intentionally referenced.
5. During implementation, advance a phase only when its prerequisite phase gates have concrete evidence. Parallel branches may proceed when their own prerequisites are satisfied; this is not strict linear `01` through `10` sequencing.
6. Do not accept document-only assertions as evidence for runtime transactional gates. Phases `05` and `06` need concrete success and failure-path tests before `07` enables user-facing profile application flows.

## Acceptance criteria

- The document set contains one focused plan for each suggested phase `01` through `10`, plus this roadmap, using the paths named in this roadmap.
- Each phase doc uses the required compact template and avoids long restatements of the design.
- Every source design section and invariant is mapped to at least one phase doc.
- Canonical definitions appear only in their owning phase and are referenced elsewhere instead of duplicated.
- Server-side profile/default files and session snapshot files are authoritative; UI localStorage is never treated as the effective/default profile source.
- Source design error handling has explicit ownership and validation for invalid explicit refs, missing global default fallback, unresolved selected packages, unknown plugin tool metadata, running-session switches, and persistence/runtime failure paths.
- Preview results and runtime capabilities are produced from shared or reconciled resolver behavior, with tests preventing diagnostic/tool-conflict drift.
- Runtime tool policy is reapplied after extension binding, reload, and late extension registration where a hook exists; if no late-registration hook exists, known binding/reload points are covered and tested.
- Migration/legacy phase gates distinguish bootstrap work from legacy runtime restore evidence.
- No phase doc assigns v1 work for prompt/theme/resource-bundle profiles, mutation of Pi `settings.json`, project default profile behavior, plugin-only post-load filtering as primary package isolation, live runtime exposure before snapshot persistence, restoring from a mutable profile ref instead of a saved snapshot, or a long-term fork of `@earendil-works/pi-coding-agent` unless the overlay approach proves impossible.
- Every stop/go gate has objective evidence that a reviewer can check before dependent phases proceed.
- Phase `10` includes the final local development smoke test in addition to code/test validation.

## Drift guardrails

Reject any phase doc or implementation plan that:

- invents capabilities outside tools, plugins/packages, and skills;
- treats profiles as prompts, themes, general resource bundles, or general settings bundles;
- mutates `~/.pi/agent/settings.json` for profile selection/application;
- makes project defaults active in v1;
- treats client localStorage as authoritative for defaults or effective session profiles;
- relies on plugin-only post-load filtering to isolate package side effects;
- lets preview diagnostics/tool conflicts diverge from runtime capabilities;
- omits runtime tool-policy reapplication after reload or known extension-binding points;
- exposes a live runtime before its capability snapshot is saved;
- restores an existing session from the current mutable profile definition instead of the saved capability snapshot;
- fails open for explicit invalid profile refs, unresolved selected capability packages, unknown plugin tool metadata that could hide conflicts, or snapshot persistence errors;
- maintains a long-term fork of `@earendil-works/pi-coding-agent` unless the pi-web overlay approach proves impossible;
- duplicates canonical schema, snapshot, settings, runtime, or UI definitions outside the owning phase;
- omits applicable invariant coverage or stop/go evidence.

## Dependencies

Phase dependency graph:

```txt
00 roadmap (traceability input; not a dependency bypass)
  -> 01-profile-schema-store-crud-api.md
      -> 03-session-snapshot-store-and-api-surface.md
          -> 02-profile-preview-resolver.md
              -> 04-profile-scoped-settings-manager-integration.md
                  -> 05-new-session-profile-application.md
                  -> 06-existing-session-restore-and-idle-profile-switch.md
                      -> 07-ui-selector-manager-wizard.md
                          -> 08-conflict-diagnostic-ux-polish.md
      -> 09-migration-and-legacy-compatibility.md (bootstrap after 01 + 03; legacy verification after 04 + 06)
          -> 10-end-to-end-validation-and-local-smoke-test.md
```

Stop/go sequencing:

- `01` must settle canonical profile and `PackageSource` validation before `02`, `03`, `04`, `07`, or `09` reference/use those shapes.
- `03` must define snapshot persistence, snapshot-specific wire types, and CAS/write-token contracts before `02` finalizes preview output and before `05` or `06` can apply snapshots transactionally.
- `02` must provide preview/diagnostic behavior before `04` relies on resolver parity or `08` displays diagnostics/conflicts.
- `04` must prove package/resource loading is profile-scoped and runtime tool policy is reapplied after extension binding/reload before `05` or `06` expose runtimes using profiles, and before `09` can complete legacy restore verification.
- `05` and `06` must prove transactional runtime/snapshot behavior with concrete failure-path tests before `07` enables user-facing profile application flows.
- `09` bootstrap work may proceed after `01` and `03`; `09` legacy restore verification is blocked on `04` and `06` runtime evidence.
- `10` cannot pass until every prior phase gate has evidence, the full invariant set I1-I12 is satisfied, and local pi-web smoke evidence is recorded.
- The roadmap feeds `10` as a traceability checklist only; it does not allow final validation to bypass unfinished phase gates.
